# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A standalone Cloudflare Worker app: a global threat intelligence dashboard, filterable by region (APJ, Europe, N. America, S. America, Middle East, Africa) with a per-country page (live OSINT feed, ransomware-leak tracker, MITRE-mapped actor profiles, INFOCON severity banner, DarkGrid-style ransomware claim map). No framework, no build step, no npm dependencies beyond `wrangler` itself.

## Commands

```bash
npm install          # installs wrangler only
wrangler dev          # run locally (npm run dev)
wrangler deploy        # deploy (npm run deploy)
wrangler tail          # stream logs from the deployed Worker (npm run tail)
curl -X POST http://localhost:8787/api/refresh   # manually trigger a collection cycle locally
```

There is no lint or test suite configured in this repo.

Local dev needs a KV namespace bound in `wrangler.toml` (`wrangler kv namespace create THREAT_DATA`, paste the id in) before `/api/data` will return anything besides "no data yet". Optional secrets go in `.dev.vars` (copy from `.dev.vars.example`): `REFRESH_KEY` (gates `POST /api/refresh` with an `x-refresh-key` header), `ABUSECH_AUTH_KEY` (enables the abuse.ch sources — free key at https://auth.abuse.ch/), `ABUSEIPDB_API_KEY` (enables the on-demand IP reputation box on the IOCs tab — free key, 1,000 checks/day), and `CF_RADAR_TOKEN` (enables real DDoS attack-traffic telemetry on the Geo Intel page — free Account > Radar > Read token from the Cloudflare dashboard). Everything else works without any of them.

## Architecture

Two independent halves connected only by `/api/data`:

- **`src/worker.js`** — the entire backend. `scheduled()` runs on two cron triggers (`wrangler.toml` → `[triggers] crons`): the full ~50-source `collect()` every 30 min (`:00`/`:30`), and a faster CVE-only `collectVulnerabilitiesOnly()` (NVD/GitHub Advisories/KEV/EPSS only) on a 10-min cadence *offset* to `5,15,25,35,45,55` rather than `*/10` — see the comment in `wrangler.toml` and on `CVE_ONLY_CRON`: at the same minute as `collect()`, the two jobs raced to read-modify-write the same KV key (`"latest"`), and the faster job (fewer sources) could read `prev` before `collect()`'s write landed, then overwrite KV afterward with that stale snapshot — silently wiping every field only `collect()` populates (`iocs`, `telegram`, `ransomwareNews`, `ddosTelemetry`) on scheduled runs while a manual `POST /api/refresh` (a single invocation, no concurrent writer) always looked fine. If a future change adds a third cron or moves either job's minutes, keep them non-overlapping. **Also check for other writers:** on 2026-09-23 an older deployment of this app under a different Worker name (`apj-threat-intel`) was found bound to the *same* `THREAT_DATA` namespace with its own `*/10` and `*/30` crons, overwriting `"latest"` with its older schema (no `iocs`/`ddosTelemetry`, 500-item cap, `actions`) — very likely the real cause of the "fields intermittently wiped" symptom above. Its cron triggers were removed (the Worker itself still exists). If data looks like it's from an older schema, list the account's Workers and their KV bindings before debugging this code. `collect()` calls fetch server-side (no CORS constraints here). All ~50 sources are fetched concurrently (`Promise.all` over one async task per source) rather than sequentially — with a sequential `await`-in-a-loop, a single slow/rate-limited host delayed every source after it in the list, which once pushed a full cycle past two minutes; concurrency bounds total wall time to roughly the slowest single source instead of the sum of all of them. Every `fetch()` goes through `fetchWithTimeout()` (`FETCH_TIMEOUT_MS`, currently 20s, via `AbortController`) so one hung/slow host degrades to a single failed `sourceStatus` entry rather than blocking the cycle — this matters most on the `POST /api/refresh` path tested with `curl`: a client-side timeout that gives up early doesn't just stop watching, Cloudflare cancels the in-flight Worker invocation along with it (visible as `Canceled` in `wrangler tail`), so testing refresh manually needs a generous client timeout (or use `run_in_background` and just wait) rather than assuming the collection keeps running server-side after the client disconnects.
  - 38 RSS/Atom feeds (`SOURCES`, parsed by `parseItems()`) — news, government CERTs (NCSC UK, JPCERT, ACSC, CERT-FR, CISA), and vendor threat-research blogs. **Not fetched by `collect()`**: they rotate through the 10-min `collectVulnerabilitiesOnly()` job, `RSS_BATCH_SIZE` (13) per run via `rssBatchForNow()` (slot picked from the wall clock), so each feed refreshes ~every 30 min. Reason: the Workers free plan caps one invocation at **50 subrequests** (redirect hops included); adding 24 feeds to `collect()` pushed it to ~70 and the overflow failed with "Too many subrequests", knocking out whichever sources started last. Current budget: `collect()` ~31, the 10-min job ~21. Check both before adding any source, and note `POST /api/refresh` runs `collect()` only, so it does not refresh RSS (`POST /api/refresh-vulnerabilities` refreshes one RSS slice).
  - structured JSON sources, each with its own parser: **GitHub Security Advisories** (`parseGithubAdvisories`, no key), **NVD** (`parseNvdCves`, no key, CVSS ≥ `NVD_MIN_CVSS` only — raw NVD volume is too high/low-relevance otherwise), **OpenPhish**'s community feed (`parseOpenPhish`, aggregated into one count+sample-domains item per day rather than one item per URL)
  - **abuse.ch** (URLhaus/ThreatFox/MalwareBazaar via `collectAbuseCh()`) — optional, gated behind `env.ABUSECH_AUTH_KEY` (their APIs require a free key as of their 2024 lockdown). Each feed contributes two things per cycle: one aggregated count+tags summary item into the main `items` feed (same reason as OpenPhish — one item per indicator would flood it), and up to `ABUSECH_IOC_CAP` (50) raw indicators per feed via `parseUrlhausIocs()`/`parseThreatfoxIocs()`/`parseMalwareBazaarIocs()` into a separate `iocs` array/KV field, deduped by `dedupeIocs()` (keyed on `source|type|value`, since the same string can be a different IOC type across feeds) and rendered as their own table on the IOCs page (`public/app.js`'s `renderIocs()`) — actual hashes/IPs/domains/URLs, not just a count, so they can be pasted into a SIEM/EDR block-list. Kept out of the main `items` feed for the same unmoderated-firehose reason as Telegram/Mastodon above.
  - ransomware.live JSON: `recentvictims` (newest ~100 worldwide) plus the full claim history of `RW_COUNTRIES_PER_RUN` (2) countries per cycle, rotating through `RW_COUNTRY_ROTATION` by wall clock via `rwCountriesForNow()` (each listed country refreshed ~every 6.5 h). This used to be India only, every cycle. The US (7MB), UK, Canada and Germany (700KB+) are deliberately not in the rotation — too big to `JSON.parse` in a Worker's CPU budget, and they dominate `recentvictims` anyway. A country's first rotation backfills up to a year of its claims at once, so right after that it can look over-represented next to countries that only accumulate from `recentvictims`. Also the CISA Known Exploited Vulnerabilities (KEV) JSON catalog
  - **MISP** (`collectMisp()`) — CIRCL's public OSINT feed (`circl.lu/doc/misp/feed-osint/`), no auth and no MISP instance needed. Fetches the `MISP_EVENT_LIMIT` (5) most recent entries from the feed's manifest concurrently, keeps the first `MISP_EVENTS_TO_KEEP` (3) that come in under `MISP_MAX_EVENT_BYTES` (2MB, checked via `Content-Length` in `fetchMispEvent()` before parsing — event size is wildly inconsistent day to day, observed 20KB to 9MB for the same feed, and a multi-MB `JSON.parse` isn't worth risking in a Worker's CPU budget; oversized days are skipped and just yield fewer IOCs, self-healing the next day), and maps each event's `Attribute` array to the common IOC shape via `parseMispEvent()`, capped at `MISP_IOC_CAP` (50) and merged into the same `iocs` array/KV field abuse.ch feeds it (deduped by the same `dedupeIocs()`). `MISP_IOC_TYPES` deliberately excludes `url` — every url-type attribute found in this feed's (currently Maltrail-sourced) daily events was a citation/reference link (a GitHub commit, a tweet, a VirusTotal GUI page), not a malicious URL, unlike abuse.ch's URLhaus where url really is the indicator.
  - **Cloudflare Radar** (`collectDdosTelemetry()`) — optional, gated behind `env.CF_RADAR_TOKEN` (a free Account > Radar > Read API token). The only *measured* DDoS signal in the app — everything else DDoS-related (leak-site claims, Telegram/Mastodon posts) is self-reported. Fetches worldwide L3/L4 attack-vector and L7 HTTP-method percentage breakdowns over the last 7 days via `fetchRadarSummary()`, stored as a separate `ddosTelemetry` KV field (not merged into `items`) and rendered as its own panel on the Geo Intel page (`public/app.js`'s `renderDdosTelemetry()`), next to the claimed-attack ticker rather than replacing it. Important caveat: Radar's attack endpoints return a normalized *percentage distribution* of attack-traffic composition (e.g. "34% of L3 attack traffic targeting India was UDP flood this week"), not raw attack counts and not per-victim confirmation — there's no way to verify any *specific* claimed attack against this data, only to see the broader real attack activity happening alongside the claims. A cycle falls back to the previous cycle's `ddosTelemetry` (`prev.ddosTelemetry`) rather than blanking the panel when all four Radar calls fail.
  - **EPSS** (Exploit Prediction Scoring System, FIRST.org, no key) — enriches, not a new item source: after each cycle's `vulnerabilities` list (NVD + GitHub Advisories + KEV, merged by CVE) is finalized, `enrichEpss()` fetches each CVE's exploitation-probability score via `fetchEpssScores()` and attaches `epss`/`epssPercentile` fields. Batched at `EPSS_BATCH_SIZE` (100) CVE IDs per request — their `cve=` param silently returns zero matches (200 OK, empty `data`) past roughly 135 comma-separated IDs in one URL rather than erroring, an undocumented URL-length cliff found empirically, so batching well under that is required. Runs on both `collect()` and the faster `collectVulnerabilitiesOnly()` cron path, since EPSS is cheap/free and this is simpler than adding a staleness check for a score that updates once daily.
  - public Telegram channels (`TELEGRAM_CHANNELS`, scraped via the unauthenticated `https://t.me/s/<handle>` web preview — no bot token/login needed — parsed by `parseTelegramChannel()`), kept in a separate `telegram` array/KV field and rendered on their own page (`public/app.js`'s `renderTelegram()`), not merged into the main `items` feed — these are unmoderated public channels, deliberately kept apart from the vetted OSINT feed. Every post must clear `CTI_RELEVANCE_KW` (or already be DDoS/AppSec-lens-tagged — a country mention alone no longer counts, since every country is taggable now) to be kept at all — unlike RSS sources, these channels post plenty of off-topic noise, so relevance is filtered at parse time rather than trusted. Posts also get a `claim` flag via `CLAIM_KW` keyword matching (actor claiming/confirming a specific breach, ransomware hit, or DDoS). Reposts (identical text, new post ID) are collapsed by `dedupeTelegram()`, keyed on `(channel, title)` rather than the link-based key `dedupeItems()` uses, since a Telegram repost is a genuinely new post ID with the same text.
    - Channels flagged `actorChannel: true` (e.g. Ummah Sec) are run by a hacktivist/threat-actor group itself, not a third-party researcher — every post is treated as a self-claim (`claim: true` unconditionally, bypassing `CTI_RELEVANCE_KW` since a bare "target + emoji" post won't trip a news-vocabulary keyword list) and the parsed `link` always points at the Telegram post itself, never at whatever leak/file-hosting URL the actor embedded — this app must never become a direct download conduit for stolen data. See `parseTelegramChannel()`.
  - Mastodon (Fediverse) sources (`RANSOMWARE_NEWS_SOURCES`) — any Mastodon hashtag or account URL natively serves a plain public RSS feed at `<url>.rss`, no login/API key/scraping trick needed, so these are parsed by the same `parseItems()` used for the RSS/Atom feeds above. Kept in their own `ransomwareNews` array/KV field and rendered as a "Community & social signal" list on the Ransomware page (`public/app.js`'s `renderRansomwareNews()`), not merged into the main `items` feed, since a public hashtag is an unmoderated firehose with zero curation. Only the two ransomware-topic sources are wired in (a `#ransomware` hashtag stream and the `@ransomwatch@infosec.exchange` leak-tracker mirror) — sibling `#threatintel`/`#cve`/`#cybersecurity` hashtag feeds were considered but left out: there's no existing page to route generic/CVE-topic content to yet, so add them (and decide where they'd surface) once that's needed rather than dumping them into the general Feed by default.

  - **IP reputation lookup** (`checkIp()`, `GET /api/ip-check?ip=`) — on-demand only, from the box at the top of the IOCs tab (`wireIpCheck()` in `app.js`); nothing is collected or scored on a schedule. Proxies AbuseIPDB `/api/v2/check` with `env.ABUSEIPDB_API_KEY` (free: 1,000 checks/day). Because it's a public endpoint on a quota'd key, it only accepts an IPv4/IPv6 literal (`isIpLiteral()`) and caches each IP's answer at the edge via the Cache API for `IPCHECK_CACHE_S` (6h) — Cache API rather than KV so lookups cost no KV writes. It has no per-visitor rate limit; if the quota gets burned by others, add a Workers Rate Limiting binding in front of it.
  - **APT Groups & Operations sheet** (`collectAptSheet()`, Florian Roth's community Google Sheet, CC BY 4.0) — a separate pipeline, not part of `items`. Runs on its own **third cron** (`APT_SHEET_CRON`, `17 3 * * *` daily; `scheduled()` checks it first) and writes its own KV keys `apt_groups` (the ~280KB group list + a 200-entry change log) and `apt_groups_meta` (per-tab SHA-1 hashes, `checkedAt`, status) — never `"latest"`, so it can't join the collect()/CVE-job read-modify-write race. Fetches 9 country tabs + Microsoft's 2023 renaming tab as public CSV (`/export?format=csv&gid=`, 10 subrequests). Built to be cheap on the common path: the sheet changes a few times a year (newest reference link as of Sep 2026 is Oct 2024), so each run hashes the raw CSVs, compares with `apt_groups_meta`, and stops if nothing changed — parse (`parseCsv()`/`parseAptTab()`), Microsoft-name mapping (`applyMsTaxonomy()`, applied only when a row's names resolve to exactly one group), diff (`diffAptGroups()`), and the big write only happen on an actual edit (~10ms CPU measured). Tab headers drift ("MITRE AT&CK", "Crowdstrike", blank columns), so `aptColumnKind()` classifies columns by pattern and treats anything unrecognised as a vendor-name column. Group ids are `tab:name` with a `#n` suffix for repeats — the sheet has several "?"/"???" rows (shown via `label`, the first alias/operation) and duplicate names. A run where any tab parses to 0 groups or the total drops >20% keeps the previous snapshot and doesn't save hashes, so it retries next day. The first run is a silent baseline (`baselineAt`). Target countries (`cc`/`rg`) come from `geoTag()` over Targets, plus Modus/Comment minus the tab's own country (`APT_TAB_CC`) — not the tab or group name, since that prose routinely says "Chinese"/"Russian" about the group itself. `APT_SCHEMA` is stored in `apt_groups_meta`; bump it when `parseAptTab()`'s output shape changes and the next run re-parses an unchanged sheet (no diff entries result, since `diffAptGroups()` doesn't compare `cc`). Served by `GET /api/actors` as the two raw KV strings concatenated (no `JSON.parse`, `max-age=3600`); `POST /api/refresh-actors[?force=1]` runs it on demand (same `REFRESH_KEY` gate). Frontend: `loadApt()` fetches it lazily the first time the Actors tab opens and renders the directory/change log (`renderApt()`); `aptCuratedRow()` adds the sheet's vendor names to matching curated `ACTORS` cards (matched by name or `aka` token, and says which sheet group it's quoting when the names differ, since that mapping is the sheet's attribution call).
  All of the above (RSS + structured sources) feed into the same `items` array and get tagged via `tagFlags()` → `geoTag()`: `cc` (ISO country codes named in the text) and `rg` (regions: `apj`/`eu`/`na`/`sa`/`me`/`af`), plus the DDoS-AppSec `lens` flag. Items stored before this carried `india`/`apj` booleans; `withGeo()` re-tags them from their text inside `dedupeItems()`/`dedupeTelegram()`, and `normItem()` in `app.js` maps them to IN/APJ until that happens. Everything then dedupes against and merges with whatever's already in KV, trims to a rolling 365-day / 1500-item (`ITEMS_CAP`, shared with `collectVulnerabilitiesOnly()` — keep it one constant or the 10-min job re-trims what the 30-min job kept) / per-region victim caps (`VICTIM_CAPS`, keyed by `ccRegion(cc)`: 500 NA, 500 Europe, 400 APJ, 150 S. America, 150 Middle East, 100 Africa, 200 unplaced — one shared cap on a date sort would let the US, ~a third of all claims, push every smaller region out; `public/app.js` mirrors it for `rwCompleteSince()`) / 100-KEV / 300-telegram / 150-ransomwareNews / 500-iocs window, and writes one JSON blob to the `THREAT_DATA` KV namespace under the key `"latest"`. 
  - `fetch()` serves two endpoints: `GET /api/data` returns the cached blob as-is (fast, can't fail from upstream timeouts/CORS since nothing is fetched on the request path); `POST /api/refresh` runs `collect()` on demand (optionally gated by `REFRESH_KEY`). Everything else falls through to static asset serving from `public/` (configured via `[assets]` in `wrangler.toml`, with `run_worker_first = ["/api/*"]` routing only API paths to the Worker).
  - Tagging is pure keyword regex — `GEO_KW` (per-country names/demonyms/cities, first entry = display name), `REGION_KW` (region-only vocabulary like "latin america", "asean"), `GEO_CASED` (case-sensitive acronyms: US, USA, UK, EU), `SOURCE_CC` (feeds that are about one country, e.g. JPCERT → JP), and `LENS_KW` — no ML/NLI. Longest match wins, so "north korean" doesn't also tag KR. Ambiguous names (Georgia, Jordan, Chad, Niger, Mali) only match their unambiguous entries. A tag means "mentions", not "victim in" — "Chinese hackers" tags CN.
  - `GET /api/radar?cc=XX` (`radarForCountry()`) — the same two Radar breakdowns for one country, for the Geo Intel page. On demand, validated, edge-cached 6h via the Cache API like `/api/ip-check`.
  - Named exports (`decode`, `tag`, `parseItems`, `parseGithubAdvisories`, `parseNvdCves`, `parseOpenPhish`, `parseTelegramChannel`, `parseUrlhausIocs`, `parseThreatfoxIocs`, `parseMalwareBazaarIocs`, `parseRwJson`, `parseKev`, `dedupeItems`, `dedupeVictims`, `dedupeKev`, `dedupeTelegram`, `dedupeIocs`, `fetchEpssScores`, `enrichEpss`, `fetchRadarSummary`, `collectDdosTelemetry`, `parseMispEvent`, `fetchMispEvent`, `collectMisp`, `collect`) exist purely so the pure-function pieces are unit-testable even though there's no test runner wired up yet.

- **`public/`** — static frontend (`index.html` + `app.js` + `styles.css`), zero build step, no bundler. `app.js` does one `fetch("/api/data")` on load and re-polls every 5 minutes (`REFRESH_POLL_MS`); all rendering (feed, ransomware panel, actor tracker, daily brief, markdown export, DarkGrid map/ticker/charts, IOC table via `renderIocs()`) is derived client-side from that one payload plus two **hand-curated, hardcoded** actor arrays (`ACTORS` and `GLOBAL_ACTORS`, each with a `geo` array of who it targets — region keys, country codes, or `"global"` — which drives the region filter and the Geo Intel page — these are not part of the collection pipeline and must be edited by hand, along with `ACTOR_META` for last-seen dates). `REGION_CC` (country → region) is duplicated between `worker.js` and `app.js` (backend for tagging and victim caps; frontend for filtering, map colours and the country picker) — keep both in sync if adding a country.
  - **Region filter**: one setting, `geo` (`apjti.geo`), set from the header segment (`[data-geo]`) or the map's region tabs via `setGeo()`. It filters the Ransomware table, Telegram/Mastodon lists, brief, snapshot, KPIs, curated actors (`actorTargetsRegion()`), the APT directory, and the map scope; Vulnerabilities and IOCs have no country data and ignore it. Region colours (`REGION_META`) are categorical DarkGrid literals, applied through a `--rc` CSS variable per element.
  - **Geo Intel page** (`#country`; it absorbed the old Map tab — `#map` and a stored `apjti.tab` of "map" land here via `parseHash()`/`showTab()`). One page, two modes: `cpCC === null` is the world/region overview, a country code is that country's profile (deep link `#country/IN`); `setCountry()` switches, `setGeo()`/the region tabs/the breadcrumb (`renderCrumb()`) go back to an overview. `buildDashboard()` renders the whole frame for the current mode: stats strip (`renderDashStats()`), map/globe, side ranking, ticker, trend (regions, or country vs its region), group/sector charts, Radar (worldwide from KV, or per country via `/api/radar` → `loadRadar()`/`radarCache`); `renderGeoBody()` renders the panels under it (overview: region news, actors, social; country: claims table with "Show all", news, actors incl. APT-sheet groups, social). Everything follows the header time window (`scopePool()` is windowed). With a country selected the map, globe and ranking keep its surroundings (`contextRegion()`) while the ticker, arcs, charts and stats narrow to it. **Two views, one selection:** Globe (default) and Flat (the dot-matrix canvas), toggled by `setView()` (`apjti.geoView`); only the visible one animates (`drawMap()` exits unless Flat is showing, the globe is `pauseAnimation()`ed otherwise). The globe (`initGlobe()`/`updateGlobe()`/`aimGlobe()`) is globe.gl from jsDelivr (pinned + SRI, ~1.9MB), loaded the first time the Globe view is shown; badges are CSS2D elements (claims per country in scope, top `GLOBE_BADGES`), the selected country gets the highlighted badge + card, and `mapScene.arcs` are drawn as animated arcs. Without WebGL or the CDN it falls back to Flat. The page is always dark (`body.map-mode`).
  - The map (`#threatMap` canvas) is a hand-rolled equirectangular dot-matrix world (`drawMap()` loop, `renderDotLayer()` cached until the view/hover/scene changes). Land comes from `world-atlas` 110m TopoJSON (jsDelivr, decoded by `topojson-client`) rasterised once by `loadAtlas()` into a 0.5° `landMask` of country indices, so a single lookup (`maskAt()`) answers both "is this land" and "which country" for hover and click. If the atlas fails to load, the map falls back to a bare graticule with pings and arcs. Region tabs and country focus animate the view toward `REGION_VIEW` bounds. Arcs (`buildMapScene()`) link countries claimed by the *same group*; they deliberately do not show attack origin, because leak-site data has no origin. Keep that caveat in the legend if you change them. When Geo Intel is active, `showTab()` sets `body.map-mode`, which switches the whole page to the dark `--dg-*` palette.
  - Chart.js (loaded via CDN in `index.html`) draws the two DarkGrid analytics charts (`chartCountries`, `chartGroups`) only; everything else is manual DOM string-building (`innerHTML +=` patterns), not a framework.
  - UI state (active filter, time window, region, actor filter, theme) persists to `localStorage` under `apjti.*` keys.
  - Theming: dark is the default and light is opt-in via the nav sun/moon toggle (`wireThemeToggle()`, stored as `apjti.theme`). An inline script in `index.html`'s `<head>` sets `html[data-theme]` before first paint so the page doesn't flash light first. It deliberately ignores `prefers-color-scheme`, because "light" is the OS default on most machines and honouring it would make light the de facto default. The dark theme only redefines the `--color-*` / `--lvl-*` tokens (`:root[data-theme="dark"]` in `styles.css`) with the neutral and accent scales inverted, so new CSS should use those tokens, not hex values, or it won't theme. White-on-colour text uses `--color-on-accent`. `body.map-mode` applies the same dark tokens, so Geo Intel is always dark. The dark block is wrapped in `@media screen`, so printed briefs are always light. The accent (`--color-accent*`, blue) is brand-only; green/yellow/orange/red come only from `--lvl-*` and mean severity (INFOCON, CVSS/EPSS, source health), so don't use them for decoration. Fonts are Manrope (`--font-body`/`--font-heading`) and IBM Plex Mono (`--font-mono`), loaded by a `<link>` in `index.html`. Map canvas and Chart.js colours are literals in `app.js` (`drawMap()`/`buildDashboard()`), so change those by hand along with the `--dg-*` tokens.
  - Header KPI row (`#kpis`, `renderKpis()`, called from `buildDashboard()` so it follows the time window): INFOCON, ransomware claims in the selected region and window, KEV added in 7 days, EPSS ≥ 50%. Shown on every tab except Geo Intel, which has its own `#dg-stats` strip. Tiles show a change vs the previous equal period only when the capped KV arrays actually cover it (`rwCompleteSince()`).
  - Vulnerabilities triage matrix (`renderVulnMatrix()`, Chart.js scatter): CVSS × log-EPSS for the rows in the current filter/search, click a point to search the table for it. CVEs with EPSS but no CVSS go in a separate left lane — every CISA KEV entry arrives without a CVSS score, so dropping them would hide all actively exploited CVEs. Colours are read from the theme tokens, so it re-renders on theme toggle.

## Editing playbook

- **New RSS/Atom source**: add `{ name, url }` to `SOURCES` in `src/worker.js`; `parseItems()` already handles RSS 2.0, RDF (`rdf:about`), and Atom (`<entry>` blocks, self-closing `<link rel="alternate" href>`, `published`/`updated`) date/link shapes generically (Atom `<entry>` support was missing until Project Zero was added — Atom-only feeds used to silently parse to 0 items, so if a new feed returns 0, check its block element first), including titleless microblog feeds (Mastodon) by falling back to the first 140 chars of the description. `decode()` unescapes XML entities *before* stripping `<tags>` — Mastodon XML-escapes its HTML instead of wrapping it in CDATA like most feeds, so the old order (strip-then-unescape) left literal `<p>`/`<a>` text in the output; keep unescape-then-strip if touching this function. Watch for feeds that put a non-publish date in `<pubDate>` — Dark Reading's "[Virtual Event] ..." listings use the *event's* future date there, and a single such item becomes the max date across the whole merged `items` array once combined with everything else, which anchors `public/app.js`'s trend chart/rolling-window logic (anything using `maxDate()`) into the future, past every item with a real date — the chart looked broken (flat lines, wrong x-axis) rather than just missing one bad item. `parseItems()` rejects dates more than `FUTURE_DATE_CUTOFF_MS` (1 day, for clock skew) ahead of now at parse time, and `dedupeItems()` renormalizes the same way on every merge (an item that ages out of a feed's own rolling window stops being freshly re-parsed and would otherwise keep a bad date forever via `prev.items` passthrough) — `maxDate()` in `app.js` also clamps to "now" as a client-side backstop. If a new source shows a similarly-wrong trend chart, check its `<pubDate>` semantics first.
- **New structured-JSON source**: write a `parseX(json)` function returning the same item shape as `parseItems()` (use `tagFlags()` for the cc/rg/lens fields), fetch it in `collect()` with its own try/catch + `sourceStatus` entry (see the GitHub Advisories / NVD / OpenPhish blocks for the pattern). If the source is IOC-firehose-shaped (many small indicators per poll, e.g. abuse.ch), push an aggregated one-summary-item-per-cycle into `items` (not one item per indicator) *and*, if the raw indicator values themselves are worth keeping (hashes/IPs/domains/URLs an analyst could actually block on), also parse them into the common `{ source, type, value, threat, tags, firstSeen, link, confidence }` shape and push onto a separate capped/deduped array/KV field rendered on its own page, rather than either field — see `collectAbuseCh()` / `parseThreatfoxIocs()` / `dedupeIocs()` / `renderIocs()` for the pattern.
- **New Telegram channel**: add `{ name, handle }` to `TELEGRAM_CHANNELS` in `src/worker.js` — but verify the handle first by actually fetching `https://t.me/s/<handle>` (curl with a browser UA) and reading a sample of its actual recent posts before adding it. Four ways a plausible-looking channel turns out to be wrong, all seen in practice: (1) squatted — the obvious handle guess resolves to an unrelated/phishing-spam channel, not the real org (happened with FalconFeeds); (2) preview disabled — the channel is real but redirects `/s/` away and needs the Telegram app/login, not fetchable server-side at all (DarkFeed, ransomwatcher, databreach); (3) real and fetchable but low-signal — production content turns out to be mostly off-topic personal/political noise rather than the on-topic feed the channel's description promises (vx-underground, dropped after a live sample showed ~0/20 relevant posts); (4) abandoned squat with a matching-ish name — a handle resolves and returns HTTP 200 but the channel has 2–12 subscribers and one "Channel created" or rename message (happened repeatedly hunting for hacktivist groups' current channels, since Telegram bans/forces migration of those constantly — check subscriber count and post dates, not just HTTP status). `CTI_RELEVANCE_KW` catches ordinary per-post noise, but it's not a substitute for actually reading a channel's real recent output before adding it — a channel that's *systemically* off-topic will still occasionally trip the keyword list. If the channel is the threat actor's own operational channel rather than a third-party researcher's, set `actorChannel: true` — see the note in Architecture above.
